# 企業級 MCP 雙層架構模型與 POC 落地實證

> **目的**：闡述在 AI 時代，為了兼顧「商業落地速度」與「企業架構安全」，為何企業平台需要將 AI 串接架構拆分為 **MCP Gateway (全域樞紐)** 與 **MCP Proxy (業務防線)** 雙層模型，並以 `mcp_poc` 專案展示其落地可行性。
> 
> **目標受眾**：CTO (關注架構、安全、防 Vendor Lock-in)、PM Head (關注營運安全、Time-to-Market)。

## 1. 雙層架構對比總覽

在傳統思維中，我們容易將 AI 與內部系統的串接視為單一節點。但在企業級應用中，為了分離「基礎設施治理」與「業務領域防護」，我們將其定義為雙層模型：

| 比較維度 | MCP Gateway (企業全域樞紐) | MCP Proxy / Server (業務領域防線) | 🌟 mcp_poc 專案落地實證 |
| :--- | :--- | :--- | :--- |
| **系統核心定位** | **統一的交通指揮中心** <br> (全局集中調度與治理) | **業務系統的最後一道防線** <br> (局部邏輯把關與執行攔截) | `mcp_poc` 本身是**右側的 Proxy 實體 (`be2-mcp`)**。它不重複造輪子，而是完美與左側既有的 `kkday API Gateway` 協作。 |
| **營運與商業應用** | **🚀 加速 AI 落地與跨團隊賦能** <br> 只要接上 Gateway，全公司的 AI 都能瞬間使用所有系統能力，零重複開發，極致縮短 Time-to-Market。 | **🛡️ 確保營運安全 (Safe AI)** <br> AI 只能「提草稿 (Change-set)」，無法直接寫入。真正修改前必須經由營運人員檢閱差異 (Diff) 並批准，保證線上資料不被搞爛。 | ✅ **已實作 Change-set 審核閉環**：<br>成功實證「AI 產出庫存/上下架草稿 → 人類在 UI 面板 (或 SSO 確認頁) 檢閱 Diff → 按下批准才真實寫入」的完整安全營運流程。 |
| **架構與企業平台** | **🏗️ 架構標準化與避免綁架** <br> 統一處理 SSO、限流與 API 計費。未來想更換底層的大型語言模型 (如從 Claude 換至 OpenAI)，內部系統完全免改。 | **💥 收斂爆炸半徑 (Blast Radius)** <br> 強制執行「讀後才能寫」、「只執行 Diff 不執行自然語言」。從結構上把 AI 幻覺與語義歧義的破壞力降至零。 | ✅ **已實作無痛身分貫穿與防護**：<br>拒絕雙重真理 (不自建 RBAC)，將核心授權完美委派給 Gateway `/verify` 代打。並透過「Scope-binding (沒讀過不准改)」阻絕 AI 幻覺目標。 |
| **權限控管方式** | **巨觀准入 (門禁系統)** <br> 攔截：「這位客服人員，有沒有權限呼叫『訂單退款 MCP』？」 | **微觀驗證 (行為稽核)** <br> 攔截：「退款金額是否算錯？是否已產生 Change-set 等待主管簽核？缺少的欄位是否想靠幻覺瞎猜？」 | ✅ **已實證分層權限驗證**：<br>Gateway 把關「商品歸屬權」(不是你的商品不能改)；MCP Proxy 把關「動作合理性」(Schema 校驗、擋下缺乏必填欄位的瞎猜)。 |
| **解決的核心痛點** | $N \times M$ 的網狀串接成本與混亂、無法全域追蹤企業內部的 AI 呼叫紀錄。 | 自然語言天生帶有的歧義與不可靠、AI 模型幻覺造成的災難性越權寫入。 | 🎯 證明了即使是最不可靠的自然語言，也能透過**結構化防禦**，安全地轉換為可稽核的電商後台寫入動作。 |
| **技術架構類比** | API Gateway (如 Kong, APISIX) | Sidecar / 兩階段提交 (Change-set 機制) | `be2-mcp` Service + SQLite Audit Store |

## 2. 營運與商業應用視角 (PM Head)

對於商業營運端而言，導入 AI 最大的疑慮往往是：「AI 會不會因為聽錯一句話，就把線上高價值的商品或訂單搞壞？」

雙層架構完美解決了這個矛盾：
1. **極速賦能 (Gateway)**：我們不再需要為每一個新的 AI 工具開發客製化串接。業務端只要提出需求，接上 Gateway，全公司的 AI 助手都能立即具備該業務能力。
2. **絕對安全的防護網 (Proxy & Change-set)**：`mcp_poc` 證明了，我們可以強制 AI 只能扮演「提案者」的角色。AI 產出的任何高風險操作（如修改庫存），都會被 Proxy 攔截並轉化為一份「待簽核的草稿 (Change-set)」。人類營運人員可以在專屬的 UI 面板上清楚看到「修改前後的差異 (Diff)」，確認無誤後按下核准，系統才會真正執行。**這確保了人類始終掌握最終控制權。**

## 3. 企業平台與架構視角 (CTO)

對於工程與架構端，雙層模型劃分了清晰的責任邊界，避免了技術債與Vendor Lock-in：

1. **基礎設施解耦 (Gateway)**：全域的路由、限流、計費、SSO 登入等，統一收斂在 Gateway。這意味著企業底層系統不需要去適應各種百花齊放的 LLM 廠商。今天用 Claude，明天換 OpenAI，後台系統完全不需改動。
2. **收斂爆炸半徑 (Proxy)**：Proxy 扮演了「護城河」的角色。我們不依賴「Prompt Engineering」來要求 AI 守規矩，而是透過結構化的程式碼 (Schema 校驗、Scope Binding) 來物理隔絕 AI 的幻覺。例如，`mcp_poc` 中的「讀後才能寫」機制，確保了 AI 絕對無法去修改一個它在當下對話中根本沒查詢過的訂單。
3. **拒絕雙重真理**：`mcp_poc` 實證了我們不需要在 MCP 層重新建立一套 RBAC 權限系統。Proxy 可以完美的將身分 (Identity) 貫穿，將物件級別的授權驗證 (Authorization) 委派回原有的 API Gateway 與後端服務，確保企業只有單一的授權真理。

## 4. 總結

企業要安全、快速地擁抱 AI，不能只靠單一的 Gateway 幫忙牽線，還必須要有 Proxy 在端點負責微觀的邏輯攔截。

`mcp_poc` 專案最大的價值在於：它沒有好高騖遠地去重寫底層設施，而是**利用公司現有的 Gateway，在其後方精準地架設了帶有 Change-set 機制的 Proxy 防線**。這證明了我們可以用極低的架構改動成本，將最高風險的電商業務安全地對 AI 開放。
