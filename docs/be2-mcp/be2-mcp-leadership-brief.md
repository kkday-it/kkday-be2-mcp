## 一頁看懂

**一句需求，交給 Agent；寫入前，人確認。** 員工用自然語言批次操作 be2 後台，AI 只能提議、產生草稿；人核准才寫入、全程留痕。

| 步驟 | be2 MCP 做什麼 |
|---|---|
| 使用者任務 | 「把這 20 個過季商品的方案下架」 |
| ① 理解目標 | 確認哪些商品/方案、範圍、風險等級 |
| ② 取得資料 | 唯讀查商品/方案/庫存現況 |
| ③ 提出變更 | 算出每筆 before→after diff |
| ④ 建立草稿 | 列出 diff，**不執行** |
| **⑤ 企業確認點** | 人看 diff → 登入核准 → 才寫入 + 稽核 |

- **治理**：前四步 agent 全自動、安全；**第五步人工確認才寫入**，agent 結構上無法自我核准。
- **現況**：核心已實作 · **195 項測試全綠** · 內網漸進上線 · 下一步跑通首次真實寫入。
- **請求**：核准 1–2 名後端 + 一個可寫帳號，**數週內就能在 production（內網、受控）看到它真的在用**。

> 以下為六個重點，想深入再看。

## 1. MCP 解決 vibe coding 的哪些隱憂

員工用 AI 加速工作是擋不住的趨勢。若沒有官方通道，需求只會走「直接打後端 API、私自寫 script」——帶來下列隱憂。be2 MCP 把每個隱憂用結構性設計擋掉：

| vibe coding 隱憂 | 沒治理會怎樣 | be2 MCP 的解法 |
|---|---|---|
| 身份不清 | script 用共用/服務帳號，查不到誰做的 | 身份貫穿本人 be2 帳號；系統不持有高權帳號 |
| AI 自主寫入無人看 | AI 直接改生產，中間沒人把關 | **draft-only**：AI 只能提議草稿，人核准才寫 |
| 無稽核軌跡 | 改了什麼、改前長怎樣查無紀錄 | 全鏈路 append-only 稽核 + 執行前後快照 |
| 越權操作 | 繞過後台既有權限檢查 | 授權委派 auth-service，越權得 fail-closed 拒絕 |
| 被誤導 / 幻覺亂改 | 被注入內容誘導、改錯商品 | 只能動本次查過的商品 + 人核准 diff + 速率上限 |
| 憑證外流 | token 散落各處、甚至離境 | be2 憑證存內網、**不離境**；給 AI 只是不透明參考 |

## 2. 執行計畫：be2 product MCP 首發（一箭雙鵰）

- **業務價值**：解 AM 高頻重複操作。近 30 天真寫入 top 操作者合計約 **13,537 筆／30 天**；單一 AM **單月手動改庫存 11,846 次**。逐筆點擊 → 一句話 + 人核准 + 批次執行。
- **風險價值**：首發不只交付 AM 效率，也用同一套治理層把 §1 六個隱憂一次擋掉——先在 be2 product 證明 pattern，再複製。
- **已實作證據**：核心已建、**195 測試全綠**；唯讀查詢已對 SIT 實機驗收；寫入治理機制 + 庫存切片已實作。
- **領域推進順序**（見 §4「領域」軸）：方案（已具備）→ 庫存（已具備）→ 價格 → 訂單 → 折扣券 → 兌換券。重用治理層，擴展成本遞減。

## 3. 架構：Stateless MCP + 企業級控制

```
員工在 Claude 用自然語言 → OAuth 登入（身份＝本人 be2 帳號；系統不持有高權帳號）
   be2-mcp（stateless 請求面 + 治理層）
   每次呼叫獨立驗證（委派 auth-service），無 session、fail-closed
   查詢(唯讀) · 提議(只建草稿不寫) · 稽核(每步留痕)
        │ 人在確認頁看 diff → 登入核准 → 才寫入      共用 store(內網)：token·草稿·稽核
        ▼                                          be2 憑證不離境
   be2 生產後台（此時才真正寫入）
```

- **Stateless MCP**：請求面不存 session、fail-closed → 可水平擴展、無 sticky session；離職/降權下次呼叫即擋。
- **企業級控制五道支柱**：身份貫穿 · 憑證不離境 · draft-only + 人工核准 · 全鏈路稽核 · 委派授權不自建 RBAC。
- **誠實**：請求面無狀態，但需持久化的（token/草稿/稽核）放內網共用 store；目前並發保護為單機實作，多實例需分散式鎖（infra 硬化，見 §5/§6）。

### 更友善：MCP Apps 互動面板 + 依風險分級的批准

用 **MCP Apps**（Claude 已官方支援）把操作做成**互動面板**——商品挑選器、視覺化 diff，非工程師點選就好、不再像命令列；渲染不出就**自動降級走文字**。批准則**依風險分級**，不一刀切：

- **L1 低風險 · 可逆**（單品上/下架）：面板一鍵確認。
- **L2 中風險 · 批次**（批次下架）：面板批准 + 逐筆意圖驗證 + 執行前重驗。
- **L3 高風險 · 不可逆**（價格/大批量）：走 agent 碰不到的 be2-auth 獨立憑證域簽核。

核准強度跟風險綁在一起——既友善又不鬆動「agent 無法自我核准」的命脈。技術細節見 `mcp-ui-exploration.md`。

各軸按自己的節奏推進（●已推進到此　◉目前所在　○尚未）：

| 軸 | 進度 |
|---|---|
| **能力** | 唯讀● · 建草稿● · 人核准執行◉ · 排程備稿○ |
| **領域** | 方案● · 庫存◉ · 價格○ · 訂單○ · 折扣券○ |
| **環境** | SIT◉ · stage○ · prod 內網○ · 公網○ |
| **人群** | 單人 pilot（下一步）· power users○ · 全組○ · 全公司○ |
| **閘門** | 逐筆人核准◉ · 低風險軟閘○ · 自動放行○ |

**怎麼讀**：能力/領域/閘門已在「實驗室」推進（程式已具備）；環境/人群還在起點——那是「上線」那半，卡在 key／可寫帳號／首次核准（＝核准後才會動的東西）。庫存程式雖已具備，但寫入契約尚未對真環境驗證（見 §6）。

## 5. 資源（人力／infra）與時程（估算，核准後 T+X）

**人力**：後端 1–2 名、QA 兼職、資安兼職、auth-service／be2-auth 少量對接、PM 定 GA 對象。

**Infra**：現況＝內網單機 + SQLite（PoC 足夠）；Production 化＝Postgres/Redis 共用 store、內網部署、告警；多實例需把單機並發鎖搬成分散式鎖。

**核心時程（到「漸進 production 內網啟用」）**：

| 里程碑 | 核准後估算 | 卡點 |
|---|---|---|
| ① 首次真實寫入（受控：單人+上下架+本人核准） | **數天–2 週** | 一把可用 key + 一個可寫帳號 |
| ② 漸進式 production 啟用（內網、緩步擴） | 滾動推進 | 使用者名單、逐 action 驗契約 |

**額外項（不併入核心估算；並行或規模放大才做）**：資安（輕量+並行）· prod key（依 rollout）· 硬化/多實例（規模放大才需要）· 擴其他領域 2–4 週/片。

## 6. 風險

| 項目 | 說明 | 狀態 |
|---|---|---|
| 首次真實寫入未跑通 | 195 測試綠但都用模擬資料；卡測試帳號無寫入權限 | 核准後即解 |
| 庫存寫入契約未雙證 | 上下架已雙證；庫存**連讀取都尚未對真環境成功過一次** → 首發用上下架規避 | 待驗 |
| per-環境/oid 授權 | 寫權限依環境與商品歸屬；pilot 帳號需在目標環境有寫權 | 待確認 |
| 並發正確性僅單機 | 多實例需分散式鎖（小規模漸進不擋） | 後段 |
| prod service key | 打正式生產需 prod key（SIT 版已取得） | 待申請 |
| 庫存/價格域盤點 | Phase 0 完整涵蓋方案域，庫存/價格待補 | Phase 3 前補 |

## 決策請求（要拍板的四件事）

1. 核准持續投入（1–2 名後端 + QA/資安兼職）。
2. 採用**漸進式 production 啟用、內網限定**的 rollout；暫不上公網。
3. 資安審查改**輕量 + 並行**（內網+draft-only 已降風險），非上線前硬 gate。
4. 協助取一把可用 key + 一個可寫帳號，讓「首次真實寫入」跑成功；prod key 依 rollout 申請。
